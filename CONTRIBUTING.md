# Правила работы с репозиторием

## Как мы работаем

Мы используем **GitHub Flow**:

- Ветка `master` всегда рабочая и готова к релизу.
- Любая задача делается в отдельной ветке, созданной от `master`.
- Все изменения попадают в `master` только через Pull Request (PR).
- Напрямую в `master` пушить нельзя.

## Порядок работы

1. Обновите `master`:
   ```bash
   git checkout master
   git pull
   ```
2. Создайте ветку под задачу:
   ```bash
   git checkout -b feat/short-description
   ```
3. Делайте небольшие коммиты с понятными сообщениями.
4. Отправьте ветку на GitHub и откройте PR в `master`:
   ```bash
   git push -u origin feat/short-description
   ```
5. Пройдите ревью и исправьте замечания.
6. После одобрения влейте PR кнопкой **Squash and merge**. Ветка удалится автоматически.

## Названия веток

- `feat/...`: новая функциональность
- `fix/...`: исправление ошибки
- `docs/...`: документация
- `chore/...`: прочее (конфиги, зависимости)

Пишите латиницей, слова через дефис: `feat/user-login`, `fix/null-pointer-in-parser`.

## Сообщения коммитов

Формат: `тип: краткое описание`.

| Тип | Когда использовать |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | изменения в документации |
| `ref` | переработка кода без изменения поведения |
| `test` | добавление или правка тестов |
| `chore` | прочее: зависимости, конфиги, обновление submodules |

Примеры:

```
feat: added user login
fix: changed logic of price calculation
docs: updated README.md
```

## Pull Request

- В описании кратко напишите, что сделано и как это проверить.
- Один PR решает одну задачу. Большие изменения лучше разбить на несколько PR.
- Чтобы влить PR, нужно:
    - минимум **1 approval** от другого участника;
    - **зелёные проверки**;
    - все комментарии в обсуждении закрыты.
- Если после аппрува вы добавили коммиты, аппрув сбрасывается, и нужно одобрение заново.
- Свой PR нельзя одобрить самому.

## Polyrepo и submodules

Проект состоит из нескольких репозиториев. Они подключены к основному репозиторию как **submodules**. У каждого репозитория свой `master`, свои PR и своё ревью.

**Клонирование:**
```bash
git clone --recurse-submodules <URL>
```
Если склонировали без флага:
```bash
git submodule update --init --recursive
```
Чтобы `pull` и `checkout` сами обновляли submodules, выполните один раз:
```bash
git config --global submodule.recurse true
```

**Если задача затрагивает submodule:**

1. Внесите изменения в репозитории самого submodule: своя ветка, свой PR, ревью, мердж в его `master`.
2. Только после мерджа обновите ссылку на submodule в основном репозитории. Создайте отдельную ветку:
   ```bash
   git checkout master
   git pull
   git checkout -b chore/bump-service-a
   git submodule update --remote service-a
   git add service-a
   git commit -m "chore: bumped service-a"
   git push -u origin chore/bump-service-a
   ```
3. Откройте PR в основной репозиторий и пройдите обычное ревью.

Основной репозиторий хранит не код submodule, а ссылку на конкретный коммит в нём. Команда `git submodule update --remote` берёт последний коммит из `master` submodule, поэтому её нужно запускать только после мерджа. Так ссылка укажет на коммит, который точно есть в `master`.
