# Сбор метаданных из S3

В dev-compose API MinIO доступен с хоста по адресу `http://localhost:9100`, консоль — по адресу `http://localhost:9101`. Создайте бакет и загрузите объекты. Для сервисов внутри Compose используется адрес `http://minio:9000`.

Создайте реализацию источника S3 (`a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a14`) через `POST /api/impls` и передайте в поле `config` JSON в виде строки. Пример содержимого строки:

```json
{
  "endpoint": "http://minio:9000",
  "bucket": "documents",
  "accessKey": "minioadmin",
  "secretKey": "minioadmin",
  "prefix": "reports/"
}
```

Обязательные поля — `endpoint`, `bucket`, `accessKey` и `secretKey`. По умолчанию используется регион `us-east-1` и сканируется весь бакет. Для временных ключей предусмотрено поле `sessionToken`. Учётной записи нужны права на перечисление бакета и чтение объектов. Для получения ACL нужны разрешения на её чтение.

`modificationTime` берётся из S3. Даты создания и последнего доступа могут поступать из пользовательских метаданных `x-amz-meta-creation-time` и `x-amz-meta-last-access-time` в формате ISO-8601. Владелец и ACL возвращаются при наличии данных. Для заглушки ACL MinIO без идентификатора получателя права `accessRights` равен `null`.

Для статистики добавьте в `config` поле `"auditLog": {"bucket": "audit", "key": "minio.jsonl"}`. Объект должен содержать экспорт аудита MinIO в UTF-8 JSON Lines. Агент считает успешные операции `GetObject` в пределах экспорта и сохраняет число чтений и дату последнего обращения. Без экспорта `accessStatistics` равен `null`. Поля `coverageStart` и `coverageEnd` в ISO-8601 задавайте только для полного экспорта за этот интервал. Исключайте из него служебные GET сканера. Без покрытия положительное событие может подтвердить недавнее использование, а нулевой счётчик не подтверждает неактивность.

## Запуск, результаты и чат

1. Вызовите `POST /api/collect/{implId}/run`. Ответ `202` содержит `requestId`.
2. Дождитесь `COMPLETED` в `GET /api/collect/runs/{requestId}`. Объекты выдаёт `GET /api/collect/runs/{requestId}/objects?offset=0&limit=50`, оценки — `GET /api/collect/runs/{requestId}/aging?offset=0&limit=50`.
3. Создайте чат и отправьте `POST /api/chats/{chatId}/messages` с полями `content` и `requestId`. Ollama получает функцию `scoreFiles` для этого запуска. Передавайте `requestId` в каждом сообщении, которому нужен набор. Обычный чат работает без этого поля.

Доступ к Impl и запускам проверяется по субъекту JWT. Для Impl, созданных до миграции, нужно назначить владельца или создать Impl заново.

Запрос поступает в `DACS_agent_request`, ответы — в `DACS_agent_response` с ключом `requestId`. Ответ содержит `requestId`, `id` реализации, `sourceId`, `batchIndex` с нуля, `status`, `items` и `error`. Батч `BATCH` содержит до `AGENTS_BATCH_SIZE` объектов, по умолчанию 50. Последнее сообщение `COMPLETED` или `FAILED` содержит пустой массив. Для длительных обходов задайте `AGENTS_MAX_POLL_INTERVAL_MS` с запасом относительно длительности сбора. По умолчанию 30 минут.

Core читает ответы в группе `dacs-core-agent-responses` и сохраняет `items` в JSONB в таблице `agent_response_batches`. Ключ `(request_id, batch_index)` защищает от повторной вставки. Kafka offset подтверждается после записи в PostgreSQL.

## Сквозная проверка

Подготовьте Keycloak и сертификаты по [инструкции запуска](SETUP.md), затем из корня выполните:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File autotests/s3-smoke.ps1 -Start
```

Сценарий заполняет бакет `dacs-s3-smoke`, создаёт временный Impl и проверяет два батча по 50 и 2 объекта, терминальный статус, префикс, хеши, SimHash, статистику и сохранение в PostgreSQL. В конце он удаляет временный Impl и оставляет тестовые данные в MinIO. В работающем окружении опустите `-Start`. Для заполнения бакета используйте `-Start -SeedOnly`. Исторические даты в тесте поступают из метаданных и экспорта аудита, а `Last-Modified` отражает время загрузки.

## Обнаружение ПДн

Детектор выключен по умолчанию. Для включения задайте `AGENTS_PII_ENABLED=true` перед запуском Agents. Он проверяет UTF-8 TXT, CSV, JSON и XML, включая UTF-8 BOM, и передаёт классификацию, версию и полноту проверки. Находки и исходный текст остаются в пределах потокового анализа. Для результатов без проверки используйте `?piiStatus=NOT_SCANNED`, для обнаружений — `?piiStatus=DETECTED`.

`AGENTS_PII_MAX_SCAN_BYTES` ограничивает анализ текста. Таймеры Actuator `dacs.s3.pii.chunk` и `dacs.s3.object.read` позволяют сравнить время обработки. Для проверки детектора добавьте к smoke-сценарию `-ExpectPii`, для проверки Ollama — `-Chat`.

## Сроки хранения

Срок определяется утверждённым реестром, в котором указаны тип документа, цель и правовое основание обработки, событие начала отсчёта, срок, исключения и ответственный. При неизвестном типе, событии или политике решение принимает ответственный. Сроки для исходных объектов, классификации в БД, Kafka и истории чата задаются отдельно. [Федеральный закон № 152-ФЗ, статьи 5, 18.1 и 21](https://mintrud.gov.ru/docs/laws/130)

## Граф зависимостей S3

- `GET /api/impls` возвращает Impl текущего пользователя.
- `GET /api/impls/{id}/s3/buckets?limit=50` возвращает бакеты из последнего успешного сбора.
- `GET /api/impls/{id}/s3/buckets/{bucket}/children?limit=50` возвращает один уровень дерева из PostgreSQL. При раскрытии папки передайте её `prefix` как URL-кодированный параметр.
- Для следующей страницы передайте `nextToken` как `continuationToken` с тем же префиксом. После нового успешного сбора обновите дерево с первой страницы.

Пока успешного сбора нет или он не обнаружил объектов, список бакетов пуст.

## Состояния ответа и подтверждение архивирования

API скоринга возвращает страницы всех файлов, включая активные. Поле `responseState` принимает `KEEP`, `WARNING` или `ARCHIVE_CONFIRMATION_REQUIRED`. Предупреждение используется для остывающих файлов, недостатка истории и результатов ПДн, требующих внимания. Чат формирует текстовое резюме.

Добавьте `archiveBucket` в JSON-конфигурацию Impl. Архивный бакет должен существовать отдельно от исходного и допускать запись с учётной записью Impl. Политика бакета определяет доступ и срок хранения копий.

1. Отправьте `POST /api/impls/{id}/s3/archive/preview` с `bucket` и `key`.
2. После подтверждения отправьте `POST /api/impls/{id}/s3/archive/confirm` с `confirmed: true` и результатом первого запроса в поле `preview`.
3. Core сверяет предпросмотр и выполняет условный серверный `CopyObject`. Ответ `ARCHIVED` содержит `archiveId` и адрес архивной копии. При изменении объекта или настроек возвращается `409`. Исходный объект остаётся доступен. Для файлов более 5 ГиБ потребуется multipart copy.

## Управление архивными копиями

Страницы архива читаются из PostgreSQL, изменения доступны владельцу Impl.

- `GET /api/impls/{id}/s3/archive?state=ARCHIVED&offset=0&limit=50` возвращает `items` и `nextOffset`. Доступны состояния `PENDING`, `ARCHIVED`, `RESTORED` и `DELETED`.
- `POST /api/impls/{id}/s3/archive/{archiveId}/restore` переводит запись в `RESTORED`. Если оригинал сохранился, сверяются ETag и версия. Если его нет, API копирует архивный объект на прежний ключ. При занятом ключе с другим объектом возвращается `409`.
- `POST /api/impls/{id}/s3/archive/{archiveId}/undo-restore` возвращает состояние `ARCHIVED`, если тот же восстановленный объект существует по исходному ключу и архивная копия доступна. При несоответствии возвращается `409`. Объект по исходному ключу остаётся на месте.
- `DELETE /api/impls/{id}/s3/archive/{archiveId}` сверяет исходный объект и архивную копию. Если файл заменён, API возвращает `409`. Затем удаляет объект по исходному ключу и архивную копию и выставляет `DELETED`. Для исходного бакета с версионированием S3 скрывает ключ маркером удаления, сохраняя предыдущие версии. Для архивной копии удаляется сохранённая версия, если она известна. Если вторая операция отклонена, можно повторить запрос после устранения причины. S3 Object Lock и политика бакета могут отклонить удаление.

Для ранее созданных архивных копий связь с исходным ключом в БД отсутствует. Перед копированием Core сохраняет запись `PENDING`. После сбоя повторите подтверждение с тем же предпросмотром. Если S3 вернул для копии другой ETag и запись нельзя сверить автоматически, она останется в `PENDING` до ручной сверки. Префикс `dacs-archive/managed/` предназначен для записей DACS.
## API вкладки «Персональные данные»

Оба запроса принимают `requestId` завершённого сбора текущего пользователя. Для неизвестного или чужого сбора возвращается `404`, для незавершённого — `409`.

- `GET /api/collect/runs/{requestId}/pii/summary` возвращает `total`, `byStatus`, `partiallyScanned` и `notChecked` по всем сохранённым файлам сбора. `partiallyScanned` включает `PARTIAL` и файлы с `DETECTED` или `REVIEW_REQUIRED`, для которых проверка была неполной. `notChecked` складывает `NOT_SCANNED`, `UNSUPPORTED` и `ERROR`. Сводные счётчики могут пересекаться со счётчиками по статусам.
- `GET /api/collect/runs/{requestId}/pii/files?status=FINDINGS&category=EMAIL&offset=0&limit=50` возвращает `items` и `nextOffset`. По умолчанию `FINDINGS` включает `DETECTED` и `REVIEW_REQUIRED`. Для всех файлов используйте `ALL`. Можно передать один из семи статусов детектора. Фильтр категории необязателен и принимает `EMAIL`, `PHONE_RU`, `SNILS`, `INN_12` или `PASSPORT_RU`.

Запись файла содержит имя, путь, статус, категории, методы обнаружения, `scanComplete` и `scannerVersion`. Исторические записи без классификации учитываются как `NOT_SCANNED`, а полнота и версия для них равны `null`. Для `NOT_DETECTED` используйте подпись «Признаки не обнаружены». Поле `retentionStatus` со значением `NEEDS_DETERMINATION` означает «Требуется определить». Поле `graph` содержит `implId`, `bucket`, `prefix` и `key` для перехода в папку файла. Граф показывает последний успешный сбор Impl, поэтому файл из более раннего сбора может отсутствовать в дереве.
